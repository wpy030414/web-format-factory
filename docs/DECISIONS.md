## ADR-001：引擎以 Mediabunny 为主干，ffmpeg.wasm 退居补缺

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：需要覆盖影像与音频两条线共 15 种输入格式的互转。直觉方案是用 ffmpeg.wasm 统一处理——
它几乎支持一切，接口也成熟。

**考虑过的方案**：

1. 纯 ffmpeg.wasm 单引擎。
2. 纯浏览器原生 API（WebCodecs + Canvas）。
3. 分层：Mediabunny（WebCodecs）为主干，ffmpeg.wasm 做补缺。

**决策**：方案 3。

**为什么选这个**：ffmpeg.wasm 比原生慢 **10–30 倍**，且因为编译时 `--disable-asm`，没有任何
硬件加速。而 Mediabunny 走 WebCodecs，能拿到硬解硬编；其官方基准比 ffmpeg.wasm 快约两个数量级。
更关键的是，**Mediabunny 的默认转换行为就是「能复用就复用」**——这正是无损换容器，
天然又快又无损。用户最常用的路径（MP4/MOV/MKV/WebM 互转、视频转音频、GIF 出入）
全部可以不用 ffmpeg。

**为什么不选其他**：方案 1 会让最常见的操作慢一个数量级，用户的第一印象就毁了。
方案 2 覆盖不到 MKV 写入与冷门编码，且要自己处理大量容器细节。

**后果**：

- ffmpeg.wasm 只在白名单场景加载，多数用户终生不会下载那 31 MB。
- 需要维护一张**例外清单**并用 lint 锁死，防止通往 ffmpeg 的路径随意增长。
- Mediabunny 完全不含图片格式，图像与动图必须自建一整层。

**何时重新审视**：若 Mediabunny 开始支持图片/动图格式，或 WebCodecs 在目标浏览器上的编码器
覆盖出现重大缺口。

## ADR-002：路由用静态表，不做能力图搜索

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：15 种格式 × 4 个引擎，理论上可以建模为一张能力图，用 BFS 搜索最短路径。

**考虑过的方案**：能力图 + BFS 搜索；静态手写路由表。

**决策**：静态表。

**为什么选这个**：

1. 边集是**静态的**，构建期已知。BFS 会合成出绕路（如 `HEIC → canvas → PNG → jsquash → JPEG`），
   要避免就得引入代价函数——而那正是全部工程知识所在。等于把复杂度从显式表格挪进了隐式权重。
2. **损失标注与图搜索天然冲突**。警告是具体路线的属性；路线若为合成，警告只能对任意链路取并集，
   产出「可能或可能不丢弃 alpha」这种正确但无用的废话。
3. **「禁用并给理由」需要理由是 `livephoto-needs-video` 这样的归因，而非「找不到路径」。**
4. **可测性**：约 225 个格式对可被穷举快照测试，毫秒级跑完。

保留「图」作为心智模型，以及一个延后的机制：若路由表超过约 60 条，再加构建期代码生成。

**后果**：路由表是唯一权威，必须保持穷举——由单元测试枚举全部格式对来守护。

**何时重新审视**：路由表条目超过约 60 条且开始出现漂移时。

## ADR-003：元数据搬运算作转换语义之内

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：初版设想把「转换格式」与「搬运元数据」视为两件事，后者属于附加功能。

**决策**：元数据是**内容**的一部分，搬运它属于转换语义之内，不是可选增强。

**为什么选这个**：`canvas.toBlob()` 会**静默抹掉**全部 EXIF / XMP / ICC 且不报错；
MP3 → M4A 若不搬运 ID3 标签，就是一次用户无法察觉的内容损失。
把这类静默损失排除在语义之外，等于允许产品对用户撒谎。

**后果**：

- 探测阶段必须读取元数据，结果报告必须清点元数据的保留情况。
- 剥离 GPS 必须是**显式开关**，且以 `critical` 级别呈现。
- 图像侧需要自建（Mediabunny 不碰图片）；影音侧由 Mediabunny 的 `raw` 与归一化字段承担。

**何时重新审视**：不再需要。

## ADR-004：Apple Live Photo 的 MOV 打标必须走 ffmpeg

- **日期**：2026-09-26
- **状态**：已采纳（**本条包含一次被实测推翻的推断，记录保留**）

**背景**：Live Photo 需要往 MOV 里写入 `com.apple.quicktime.content.identifier`。
如果主干引擎能做，就不必为此拖入 31 MB 的兜底引擎。

**被推翻的推断**：查阅 Mediabunny 类型定义时发现 `MetadataTags.raw` 字段，其文档注释写明
*"When writing, it can be used to set arbitrary metadata tags in the output file… MP4/QuickTime…
the keys reflect the keys specified there (such as `'com.apple.quicktime.version'`)"*。
据此曾推断主干引擎可以直接写入该键，并认为「Live Photo 封装不需要 ffmpeg」。

**实测否定了该推断**：

| 测试入参 | 结果 |
| --- | --- |
| 无轨道 MOV + `raw` 长键 | 键被丢弃 |
| **真实 MP4 → MOV 复用 + `raw` 长键** | **键仍被丢弃**（无 `keys`、无 `ilst`、无 UUID 字符串） |
| `raw` 键 `©cmt`（4 字符） | ✅ 键与值均写入 |
| `raw` 键 `com.apple.quicktime.version` | ❌ 键被丢弃 |

**结论**：`raw` 写入**只支持 4 字符的 `ilst` 原子名**；长格式 QuickTime `keys` 键会被静默丢弃。
文档中举 `com.apple.quicktime.version` 为例，描述的其实是**读**方向。

**决策**：Apple Live Photo 的 MOV 打标经 ffmpeg 完成，命令为
`-c copy -movflags use_metadata_tags -metadata com.apple.quicktime.content.identifier=<UUID>`。
**`-movflags use_metadata_tags` 是必需的**——省略它会写出 `udta` 标签而非 `keys`/`ilst`，
`ffprobe` 读不到，且**不报错**。

**为什么不选其他**：手写 MOV 原子手术可行但风险高，且需自行保证产物能被 Apple Photos 识别。
作为代价，此路径需要 31 MB 引擎，**必须在 UI 上如实告知用户**。

**后果**：

- Live Photo 的生成属于重型路径，纳入 ffmpeg 例外白名单。
- **流程教训**：「接口存在」不等于「行为生效」。凡承载关键路径的假设，
  一律以真实产物的探针为准，不以类型定义或文档措辞为准。该教训已写入 `AGENTS.md`。

**何时重新审视**：若 Mediabunny 增加对 QuickTime `keys` 原子的写入支持。

## ADR-005：PWA 只预缓存应用外壳，绝不预缓存 WASM

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：产品要求离线可用（PWA）。直觉上应当把引擎一并预缓存以保证离线可转换。

**决策**：预缓存只包含应用外壳；WASM 引擎在首次使用时按需下载并**运行时缓存**。

**为什么选这个**：单份 ffmpeg 核心解包 64 MB（esm + umd 各约 31 MB 的 wasm）。
预缓存会让「安装应用」变成一次 31 MB 起步的下载，而绝大多数用户从不需要兜底引擎——
主干与图像两层覆盖了常用路径。运行时缓存让启动保持轻量，同时首次用到引擎之后依然可离线。

**后果**：首次使用兜底引擎需要下载，必须给出字节级进度提示，而非一个转圈。
缓存写入失败（配额不足）时降级为仅网络，并提示一次。

**何时重新审视**：若离线场景被证实普遍需要兜底引擎。

## ADR-006：产品边界收口在编码参数 schema

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：主干引擎的 `ConversionOptions` 暴露了 `width` / `height` / `fit` / `crop` /
`rotate` / `flip` / `frameRate` / `postProcess`，而产品范围只允许「转换 + 编码参数」。

**决策**：产品边界**只在一个地方**收口——`src/core/registry/formats.ts` 的 `SCOPE_ALLOWLIST`，
并由单元测试断言每个 `ParamSpec` 的 id 都在其中。引擎层的能力不构成产品层的许可。

**为什么选这个**：这是**将来最容易被顺手破坏**的约束——某个下午有人觉得「顺手加个缩放很合理」，
产品的语义就此改变。把边界做成一份需要刻意修改的清单，比写在文档里有效。

**后果**：新增任何参数都必须显式修改该清单。缩放、裁剪、帧率等参数在引擎层存在但永不暴露。

**何时重新审视**：若产品决定增加编辑能力——届时应当是**新开一个模式**，而不是混入转换网格。

## ADR-007：保真度取源与目标的较大有损度

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：判断一次转换是否「无损」，直觉做法是看目标格式是否有损。

**决策**：保真度 = `max(源编码的有损度, 目标编码的有损度)`。
有损源转无损格式必须给出 `generation-loss-from-lossy-source`。

**为什么选这个**：MP3 → FLAC 按编码器算无损，**按内容算是在说谎**——
用户得到的是一个更大、音质毫无改善的文件。同理，WAV → FLAC 判为无损是正确的
（FLAC 是 PCM 的无损压缩）。

**后果**：结果报告需要同时知道源编码与目标编码。这条警告极可能是全产品最能建立信任的细节。

**何时重新审视**：不再需要。

## ADR-008：许可证不构成约束

- **日期**：2026-09-26
- **状态**：已采纳（由项目所有者决定）

**背景**：ffmpeg 核心因链接 libx264/libx265 而是 GPL-2.0-or-later；
gifski 是 AGPL-3.0；libheif 是 LGPL-3.0。

**决策**：项目所有者明确接受任何传染性许可证。技术上仍保持引擎按需加载，
但理由是**体积与性能**，不再是许可证的可分离性。

**后果**：可直接使用画质最好的 GIF 编码器（gifski，带跨帧时域抖动）。
须注意 H.264/H.265 的**专利池**问题是独立于著作权许可的商业风险。

**何时重新审视**：若项目转向商业分发。
