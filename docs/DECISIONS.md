## ADR-001：引擎以 Mediabunny 为主干，ffmpeg.wasm 退居补缺

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：需要覆盖影像与音频两条线共 15 种输入格式的互转。直觉方案是用 ffmpeg.wasm 统一处理——
它几乎支持一切，接口也成熟。

**考虑过的方案**：

1. 纯 ffmpeg.wasm 单引擎。
2. 纯浏览器原生 API（WebCodecs + Canvas）。
3. 分层：Mediabunny（WebCodecs）为主干，ffmpeg.wasm 做补缺。

**决策**：方案 3。

**为什么选这个**：ffmpeg.wasm 比原生慢 **10–30 倍**，且因为编译时 `--disable-asm`，没有任何
硬件加速。而 Mediabunny 走 WebCodecs，能拿到硬解硬编；其官方基准比 ffmpeg.wasm 快约两个数量级。
更关键的是，**Mediabunny 的默认转换行为就是「能复用就复用」**——这正是无损换容器，
天然又快又无损。用户最常用的路径（MP4/MOV/MKV/WebM 互转、视频转音频、GIF 出入）
全部可以不用 ffmpeg。

**为什么不选其他**：方案 1 会让最常见的操作慢一个数量级，用户的第一印象就毁了。
方案 2 覆盖不到 MKV 写入与冷门编码，且要自己处理大量容器细节。

**后果**：

- ffmpeg.wasm 只在白名单场景加载，多数用户终生不会下载那 31 MB。
- 需要维护一张**例外清单**并用 lint 锁死，防止通往 ffmpeg 的路径随意增长。
- Mediabunny 完全不含图片格式，图像与动图必须自建一整层。

**何时重新审视**：若 Mediabunny 开始支持图片/动图格式，或 WebCodecs 在目标浏览器上的编码器
覆盖出现重大缺口。

## ADR-002：路由用静态表，不做能力图搜索

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：15 种格式 × 4 个引擎，理论上可以建模为一张能力图，用 BFS 搜索最短路径。

**考虑过的方案**：能力图 + BFS 搜索；静态手写路由表。

**决策**：静态表。

**为什么选这个**：

1. 边集是**静态的**，构建期已知。BFS 会合成出绕路（如 `HEIC → canvas → PNG → jsquash → JPEG`），
   要避免就得引入代价函数——而那正是全部工程知识所在。等于把复杂度从显式表格挪进了隐式权重。
2. **损失标注与图搜索天然冲突**。警告是具体路线的属性；路线若为合成，警告只能对任意链路取并集，
   产出「可能或可能不丢弃 alpha」这种正确但无用的废话。
3. **「禁用并给理由」需要理由是 `livephoto-needs-video` 这样的归因，而非「找不到路径」。**
4. **可测性**：约 225 个格式对可被穷举快照测试，毫秒级跑完。

保留「图」作为心智模型，以及一个延后的机制：若路由表超过约 60 条，再加构建期代码生成。

**后果**：路由表是唯一权威，必须保持穷举——由单元测试枚举全部格式对来守护。

**何时重新审视**：路由表条目超过约 60 条且开始出现漂移时。

## ADR-003：元数据搬运算作转换语义之内

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：初版设想把「转换格式」与「搬运元数据」视为两件事，后者属于附加功能。

**决策**：元数据是**内容**的一部分，搬运它属于转换语义之内，不是可选增强。

**为什么选这个**：`canvas.toBlob()` 会**静默抹掉**全部 EXIF / XMP / ICC 且不报错；
MP3 → M4A 若不搬运 ID3 标签，就是一次用户无法察觉的内容损失。
把这类静默损失排除在语义之外，等于允许产品对用户撒谎。

**后果**：

- 探测阶段必须读取元数据，结果报告必须清点元数据的保留情况。
- 剥离 GPS 必须是**显式开关**，且以 `critical` 级别呈现。
- 图像侧需要自建（Mediabunny 不碰图片）；影音侧由 Mediabunny 的 `raw` 与归一化字段承担。

**何时重新审视**：不再需要。

## ADR-004：Apple Live Photo 的 MOV 打标必须走 ffmpeg

- **日期**：2026-09-26
- **状态**：已采纳（**本条包含一次被实测推翻的推断，记录保留**）

**背景**：Live Photo 需要往 MOV 里写入 `com.apple.quicktime.content.identifier`。
如果主干引擎能做，就不必为此拖入 31 MB 的兜底引擎。

**被推翻的推断**：查阅 Mediabunny 类型定义时发现 `MetadataTags.raw` 字段，其文档注释写明
*"When writing, it can be used to set arbitrary metadata tags in the output file… MP4/QuickTime…
the keys reflect the keys specified there (such as `'com.apple.quicktime.version'`)"*。
据此曾推断主干引擎可以直接写入该键，并认为「Live Photo 封装不需要 ffmpeg」。

**实测否定了该推断**：

| 测试入参 | 结果 |
| --- | --- |
| 无轨道 MOV + `raw` 长键 | 键被丢弃 |
| **真实 MP4 → MOV 复用 + `raw` 长键** | **键仍被丢弃**（无 `keys`、无 `ilst`、无 UUID 字符串） |
| `raw` 键 `©cmt`（4 字符） | ✅ 键与值均写入 |
| `raw` 键 `com.apple.quicktime.version` | ❌ 键被丢弃 |

**结论**：`raw` 写入**只支持 4 字符的 `ilst` 原子名**；长格式 QuickTime `keys` 键会被静默丢弃。
文档中举 `com.apple.quicktime.version` 为例，描述的其实是**读**方向。

**决策**：Apple Live Photo 的 MOV 打标经 ffmpeg 完成，命令为
`-c copy -movflags use_metadata_tags -metadata com.apple.quicktime.content.identifier=<UUID>`。
**`-movflags use_metadata_tags` 是必需的**——省略它会写出 `udta` 标签而非 `keys`/`ilst`，
`ffprobe` 读不到，且**不报错**。

**为什么不选其他**：手写 MOV 原子手术可行但风险高，且需自行保证产物能被 Apple Photos 识别。
作为代价，此路径需要 31 MB 引擎，**必须在 UI 上如实告知用户**。

**后果**：

- Live Photo 的生成属于重型路径，纳入 ffmpeg 例外白名单。
- **流程教训**：「接口存在」不等于「行为生效」。凡承载关键路径的假设，
  一律以真实产物的探针为准，不以类型定义或文档措辞为准。该教训已写入 `AGENTS.md`。

**何时重新审视**：若 Mediabunny 增加对 QuickTime `keys` 原子的写入支持。

## ADR-005：PWA 只预缓存应用外壳，绝不预缓存 WASM

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：产品要求离线可用（PWA）。直觉上应当把引擎一并预缓存以保证离线可转换。

**决策**：预缓存只包含应用外壳；WASM 引擎在首次使用时按需下载并**运行时缓存**。

**为什么选这个**：单份 ffmpeg 核心解包 64 MB（esm + umd 各约 31 MB 的 wasm）。
预缓存会让「安装应用」变成一次 31 MB 起步的下载，而绝大多数用户从不需要兜底引擎——
主干与图像两层覆盖了常用路径。运行时缓存让启动保持轻量，同时首次用到引擎之后依然可离线。

**后果**：首次使用兜底引擎需要下载，必须给出字节级进度提示，而非一个转圈。
缓存写入失败（配额不足）时降级为仅网络，并提示一次。

**何时重新审视**：若离线场景被证实普遍需要兜底引擎。

## ADR-006：产品边界收口在编码参数 schema

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：主干引擎的 `ConversionOptions` 暴露了 `width` / `height` / `fit` / `crop` /
`rotate` / `flip` / `frameRate` / `postProcess`，而产品范围只允许「转换 + 编码参数」。

**决策**：产品边界**只在一个地方**收口——`src/core/registry/formats.ts` 的 `SCOPE_ALLOWLIST`，
并由单元测试断言每个 `ParamSpec` 的 id 都在其中。引擎层的能力不构成产品层的许可。

**为什么选这个**：这是**将来最容易被顺手破坏**的约束——某个下午有人觉得「顺手加个缩放很合理」，
产品的语义就此改变。把边界做成一份需要刻意修改的清单，比写在文档里有效。

**后果**：新增任何参数都必须显式修改该清单。缩放、裁剪、帧率等参数在引擎层存在但永不暴露。

**何时重新审视**：若产品决定增加编辑能力——届时应当是**新开一个模式**，而不是混入转换网格。

## ADR-007：保真度取源与目标的较大有损度

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：判断一次转换是否「无损」，直觉做法是看目标格式是否有损。

**决策**：保真度 = `max(源编码的有损度, 目标编码的有损度)`。
有损源转无损格式必须给出 `generation-loss-from-lossy-source`。

**为什么选这个**：MP3 → FLAC 按编码器算无损，**按内容算是在说谎**——
用户得到的是一个更大、音质毫无改善的文件。同理，WAV → FLAC 判为无损是正确的
（FLAC 是 PCM 的无损压缩）。

**后果**：结果报告需要同时知道源编码与目标编码。这条警告极可能是全产品最能建立信任的细节。

**何时重新审视**：不再需要。

## ADR-008：许可证不构成约束

- **日期**：2026-09-26
- **状态**：已采纳（由项目所有者决定）

**背景**：ffmpeg 核心因链接 libx264/libx265 而是 GPL-2.0-or-later；
gifski 是 AGPL-3.0；libheif 是 LGPL-3.0。

**决策**：项目所有者明确接受任何传染性许可证。技术上仍保持引擎按需加载，
但理由是**体积与性能**，不再是许可证的可分离性。

**后果**：可直接使用画质最好的 GIF 编码器（gifski，带跨帧时域抖动）。
须注意 H.264/H.265 的**专利池**问题是独立于著作权许可的商业风险。

**何时重新审视**：若项目转向商业分发。

## ADR-009：不写 `still-image-time` 轨道——宁缺，不凭二手描述手写

- **日期**：2026-09-26
- **状态**：已采纳；**2026-09-26 补记：解锁条件已满足，且实测它并不影响配对**（见「后果」）

**背景**：Apple 的 Live Photo MOV 除 content identifier 外，还带一条
`com.apple.quicktime.still-image-time` **定时元数据轨道**，标记静帧在视频时间轴上的位置。
我们的产物没有它。这是「已知缺口」清单上的最后一项，也是全项目不确定性最高的一处。

**已查实的是语义**（两个相互独立的来源说法一致）：它是一条定时元数据轨道，键为
`com.apple.quicktime.still-image-time`，样本载荷为单字节 `0xFF`，而**这个值本身没有意义**——
有意义的是该样本的呈现时间戳，它才是静帧的位置。

**未查实的是字节**：`trak` / `mdia` / `stbl` 乃至 `mebx` 样本条目究竟如何摆放。
公开的 Swift 实现把这段交给 AVFoundation，交出的因此是语义而非布局；几份广为流传的格式分析
同样只描述「是什么」，不描述「长什么样」。

**考虑过的方案**：

1. 按二手描述手写 `moov` 盒树，再用 `ffprobe` 验证结构。
2. 找到一份 Apple 亲自产出的 MOV 作为参照物，从其字节反推布局。
3. 不写，把缺口与理由一并记录下来。

**决策**：方案 3。

**为什么选这个**：方案 1 正是 ADR-004 记录下来的那次失败——凭类型定义与文档措辞推断
「接口存在即行为生效」，最后靠真实产物的探针才推翻。两次的形状一模一样：一处关键路径上的假设，
唯一的证据是关于它的**描述**，而不是**产物本身**。差别在于代价：ADR-004 那次付出的只是一个
错误的封装修复方案；这一次若写错，代价是一棵畸形的盒树——**整个 `.livp` 可能因此打不开**，
远糟于缺一条可选轨道。

还有一层：方案 1 的验证是不完整的。`ffprobe` 确实能读 `mebx` 轨道，所以**结构有效性可验**；
但 **Apple 设备是否接受这份产物，在这台机器上无法验证**。也就是说最好的情况下，交出去的仍是
一个「结构看起来对、但没人真正打开过」的文件——而它的实际效果，恰恰是本项目最不该猜的地方。

**为什么不选方案 2**：它其实是最好的方案，只是需要一份现在没有的输入。

**后果**：

- 写出的 MOV 比 Apple 自己的产物少一条可选轨道，已在结果面板以 `info` 级损失如实标注。
  **2026-09-26 补记**：实测它**不影响**相册是否把两半认成一张实况照片——把 Apple 那三条
  元数据轨道全部拆掉，配对照样成立。它仍是与 Apple 产物的一处差异，但**不是**配对失败的
  成因，写清楚免得它当替罪羊（见 `docs/researches/live-photo-photos-import.md` §6.1）。
- **解锁条件已满足（2026-09-26）**：参照物拿到了，实测结论在那份研究文档里——那条轨道确实
  没写，但它**也不是**相册认不认的关键；真正缺的是静图的 MakerNote 标识与视频 `moov/meta`
  的形态，那两样已经补上，并在真机上端到端验收过。
- 「Apple 设备的接受度未经实测」这句交付说明可以删了：macOS 侧已实测（导入相册即成为实况
  照片），iOS 侧也已实测（文件导入不配对，须经由相册隔空投送）——两边的结论都在研究文档里。

**何时重新审视**：一旦手上有了真实的 Apple Live Photo MOV，或出现了可靠的字节级规范。

## ADR-010：能力闸门与语义判定分成两层

- **日期**：2026-09-26
- **状态**：已采纳

**背景**：诊断页的正文里一直写着这样一句：

> 转换器只提供它探测到确实可用的路由，所以这一页也解释了「为什么某个目标格式在这里是灰的」。

**那是一句假话。** `planFor()` 根本不接收任何能力信息，`Capabilities` 全项目只喂给那一页自己。
界面上的按钮不看任何探测结果。后果是具体的：「动态 WebP → 视频」在 Safari 上（没有
`ImageDecoder`）按钮亮着、点了才失败；「视频 → 动态 WebP」在缺 COOP/COEP 的页面上同样亮着
点不动——而兜底引擎在这种情况下**不是报错，是挂起**。

**考虑过的方案**：

1. 把能力判断并进 `verdictFor()`，让它一次回答完。
2. 单独一层闸门，在 `planFor()` 里叠加在语义判定之后。
3. 不接，继续让作业在最后失败。

**决策**：方案 2。

**为什么选这个**：方案 1 会让 `verdictFor()` 的答案**随运行它的机器而变**，而那张
225 对的穷举测试正是建立在「同一对格式在任何机器上结论一致」之上的——混进去，测试就锁不住
任何东西了。分成两层之后，下层回答「这在任何机器上是否**可能**」，上层回答「在**这台**机器上
是否可能」，各自都能被干净地测。

方案 3 的代价不是「偶尔失败」，而是**理由的缺席**：一条被提供、最后才失败的路由，
和一条被禁用并说明原因的路由，教给用户的东西完全不同。这个项目存在的理由就是前者。

**后果**：

- 路由的穷尽性测试仍按语义层跑；闸门另有测试，并逐一钉住「开得太宽」的三种情形
  （见 `docs/specs/engine-routing.md` 的「三条必须守住的边界」）。
- `planFor()` 的 `caps` 是**必填**参数，不给默认值——默认只能是乐观或悲观之一，
  而那个决定不该由被调用方替调用方做。
- 诊断页那句话现在为真了。**在它变真之前，它已经假了很久**——这一条本身值得记下来：
  一句写在界面上的承诺，如果没有代码守着，就会一直假下去，而且没人会收到通知。

**何时重新审视**：若闸门的条数增长到需要按格式逐条声明，而不是按能力声明。

## ADR-011：参数刻度在引擎边界收口，且只保留一份

- **日期**：2026-09-26
- **状态**：已采纳（**本条记录一次由端到端测试抓出的失败**）

**背景**：参数面板上的「质量」是 0–100，而 Mediabunny 的 `Quality` 是 0–1。
换算在这个仓库里有三份拷贝：图像引擎写了（`normalizeQuality`），另外两处没写。

**这个错误有两个面孔，其中一个完全安静**：

- **VP9 / WebM**：Mediabunny 从 quality 推 quantizer，并把越界值**夹回合法区间**
  （它自己的注释就写着 *"the quality may lie outside the 0-1 range, we clamp"*）。
  于是 VP9 静默地按**最高质量**编码，那条滑块完全不起作用——而它「成功」了。
- **H.264 / MP4·MOV·MKV**：浏览器没有 quantizer 模式可退，只能退回按错误刻度算出的比特率
  ——`0.3·e^(2.5538·75)`，约 `3.7×10^86 bps`——编码器直接拒收整个配置。

也就是说「动图 → MP4/MOV/MKV」是一条**被提供、却只能失败的路由**，而它此前一条测试都没有。
抓到它的不是单元测试，是把「动图 ↔ 视频」整张矩阵铺开、逐格验产物的那次端到端。

**决策**：换算收进 `src/engines/types.ts` 的 `qualityFraction()`，三个引擎共用；图像引擎
原有的私有实现一并删除。

**为什么选这个**：三份拷贝不是三倍安全，是三倍的漏掉机会，而漏掉的那一份不会报错。
收成一处之后，第四次漏掉在编译期就不可能。

**后果**：

- 端到端矩阵成为这条路由的守门人；12 条方向全部验产物（容器、编码、ISO-BMFF 品牌）。
- 教训写进了 `AGENTS.md`：**一个被夹回合法区间的非法值不会报错**，
  所以「它跑通了」不等于「它按你说的跑了」。
- 同一个 bug 的第二处（用户拖动质量滑块时的视频/音频目标）只在你动过那个滑块时才触发，
  因为参数面板的默认值被 `changedParams` 滤掉了——**比第一处更隐蔽**。

**何时重新审视**：不再需要——刻度只有一处了。

## ADR-012：location 层的 `types` 是替换语义——样例配置在真机上咬的第一口

- **日期**：2026-09-26
- **状态**：已采纳（**本条记录一次在真实服务器上暴露的失败**）

**背景**：`deploy/` 下的 nginx 样例此前从未上过真机（README 的已知限制里写着这一点）。
2026-09-26 它第一次被部署到一台 nginx/1.28.3 (Ubuntu) 上，于是拿到了第一份真机证据。

**症状**：`GIF → Live Photo` 失败，控制台里只有一行：

```
TypeError: 'application/octet-stream' is not a valid JavaScript MIME type
  for module script 'https://…/engines/ffmpeg/const.js'
```

`const.js` 是 ffmpeg.wasm 那个 module worker 的第一层 `import`（`worker.js` 里
`import './const.js'`）。它加载不了，`FFmpeg.load()` 就既不 resolve 也不 reject——
界面停在「转换中」。还是这个形状：**没有报错的那种坏**（同 ADR-005、ADR-010）。

**根因**：样例的 `location /engines/` 里写着 `types { application/wasm wasm; }`，
而这在 nginx 里不是「补一条」，是**换掉整张表**。合并逻辑只有一句
（`ngx_http_core_module.c`）：

```c
if (conf->types == NULL) {
    conf->types = prev->types;
    conf->types_hash = prev->types_hash;
}
```

本层声明了自己的 `types`，上层（http 层的 `include mime.types;`）那张表就不再继承。
没列出的扩展名一律落到 `default_type`，而 Ubuntu 的 `nginx.conf` 把它设成
`application/octet-stream`。于是 `.wasm` 活着，`.js` 死了。

**证据**（同一次巡检的 `curl -sI`，对错并存——所以不是「服务器坏了」，而是「这一层换了表」）：

| 路径 | Content-Type | |
| --- | --- | --- |
| `/assets/index-…js` | `application/javascript` | ✅ 没声明 types 的 location |
| `/sw.js` | `application/javascript` | ✅ 同上 |
| `/engines/ffmpeg/ffmpeg-core.wasm` | `application/wasm` | ✅ 被显式声明了 |
| `/engines/ffmpeg/const.js` | `application/octet-stream` | ❌ 被换掉的那张表里没有它 |
| `/engines/ffmpeg/ffmpeg-core.js` | `application/octet-stream` | ❌ 同上 |

**决策**：`/engines/` 的 `types` 块把该目录真正用到的扩展名**列全**（`wasm` 与 `js`），
并在注释里写明它是替换语义；`location = /manifest.webmanifest` 那处同形态的写法补一句
为什么在那里安全（`=` 精确匹配，只可能命中一个文件）。

**为什么不干脆删掉整个块**：nginx ≥ 1.21.6 的 `mime.types` 已自带 `application/wasm`，
所以在咬人的那台 1.28.3 上删掉它也能工作。但 Ubuntu 22.04 与 Debian 11 装的都是 1.18，
没有这一条——样例要能被照抄到老机器上，所以显式声明保留，只把它补全。

**为什么参考服务器抓不到它**：`scripts/serve-deploy.mjs` 是用一张手写的 MIME 表实现的，
它当然把 `.js` 映对了——**它不是 nginx，也就复现不了 nginx 的换表语义**。
「产物侧全绿」与「真机上失败」并不矛盾，它们量的是两件事。

**后果**：

- 单元测试补上了配置侧的断言：前缀匹配的 location 一旦声明 `types`，必须自己补回 `.js`。
  原先那条只检查「文件里出现过 `application/wasm`」——**它在坏掉的配置上同样成立**，
  这正是它当初没拦住的原因。新断言已用「退回旧配置」的方式验证过会红。
- nginx 样例头部带上了部署后自检（三条 `curl -sI`），错的那条会直接暴露出来。
- 缓存把这次失败又延长了一截：`/engines/` 的响应是 `max-age=604800`，Service Worker
  那边还是 `CacheFirst` 一年。**配置修好之后，已经访问过的浏览器仍会从缓存里拿到那份
  octet-stream 的副本**，直到站点数据被清掉或缓存过期。修配置与清缓存是两件事。
- Caddy 那份补了一句「别照着 nginx 这份往这里补 MIME 声明」——Caddy 的 MIME 表是全局的，
  没有这回事。

**何时重新审视**：若引擎资源改为带版本目录的路径（`/engines/ffmpeg-0.12.10/…`），
那次改动会顺带绕开上面的缓存问题；MIME 声明本身则不能取消。

## ADR-013：GIF 的帧时序以毫秒为单位，20 毫秒是可用下限

- **日期**：2026-09-26
- **状态**：已采纳（**本条记录一次由产物字节抓出的失败**）

**背景**：用户报告「视频转 GIF 时，产物 GIF 的帧率会很低，没有匹配视频的帧率」。
问题不在浏览器能否解码，也不在编码器快慢，而在**喂给编码器的时间单位错了 10 倍**。
完整实测见 `docs/researches/gif-frame-timing.md`，探针脚本在
`scripts/probes/gif-delay-unit.mjs`。

**根因**：`modern-gif` 的 `delay` 参数收的是**毫秒**（解码器 `delayTime * 10`），
而 `videoToGif` 传的是**厘秒**。写盘时 `delay / 10` 又被**向零截断**，于是
30fps 源的 `3` 变成 `0`、60fps 源的 `2` 变成 `0`——每一帧的 `delayTime` 都是 `0`。

**为什么在浏览器里看不出来**：`delayTime` 为 0（或 1）时，渲染器按 Netscape 时代的
兼容规则把它抬到 **100 毫秒**。而样本视频恰好是 10fps，正确值也是 100 毫秒，于是界面
上一切正常；只有产物文件里写着「10 帧、总长 0.1 秒」。**这个错误只在字节里可见。**

**证据**（`node scripts/probes/gif-delay-unit.mjs`，回读 Graphic Control Extension）：

| 传入 `delay` | 写进文件的 `delayTime` | 解码器读回 |
| --- | --- | --- |
| `3`（旧代码对 30fps 源算出的值） | **0** | 100ms |
| `2`（旧代码对 60fps 源算出的值） | **0** | 100ms |
| `17` | 1 | 10ms（截断，不是四舍五入） |
| `30`（GIF → GIF 路径当时传的值） | 3 | 30ms ✅ |

**决策**：

1. 引擎内部的时间单位统一为**毫秒**，`DecodedFrame.delay` 的文档随之改正（它此前
   写着「centiseconds, as stored in the GIF」，而两个生产者一个给毫秒、一个给厘秒）。
2. 交给编码器的延迟一律**吸附到 10 毫秒栅格**，并按**累积时间戳**对齐（帧 i 的延迟 =
   `snap(end_i) − snap(end_{i-1})`），而不是逐帧各自取整。累积对齐既消除了漂移，又让
   编码器的截断成为空操作。
3. **20 毫秒是可用下限**，且这一条写在格式注册表里（`GIF_FRAME_TIMING`），引擎与损失
   模型读同一份。栅格（10ms）与下限（20ms）是两个数，不是同一个数。
4. 源快于 50fps（手机常见的 60fps）时**保时长、丢帧**：按 20 毫秒槽位抽帧，取每槽中心
   之前最近的一帧。装不下的帧由损失模型如实报告为「部分帧将被丢弃」。

**为什么不用 10 毫秒作下限**：格式能*表达* 10 毫秒，渲染器不*认*——低于 20 毫秒的值被
抬到 100 毫秒。照着格式上限写，得到的不是更流畅的动画，而是一帧跑 100 毫秒的动画，
比慢更糟：它是不均匀的。

**为什么不选「保帧数、放慢」**：60fps 的 1 秒要装进 50fps 的容器，另一种牺牲是**时长**：
60 帧各占 20 毫秒，1 秒变 1.2 秒，运动速度也错了。保时长、丢帧至少让产物与源**同时开始、
同时结束**，而丢帧这件事是可以被说出来的。

**为什么不是「拒绝转换」**：60fps 手机视频是最常见的输入之一，拒绝等于把这条路由关掉。
`AGENTS.md` 的非目标条款约束的是**不暴露帧率参数**，而这里没有新增任何 `ParamId`，
用户无从选择——真正的约束是「损失必须计算，不得写死」，正是本轮补上的东西。措辞上把
它定位为**损失**而非**编辑**：没有任何人在这里选择了帧率。

**后果**：

- `frame-timing-quantized` 与 `frames-dropped` 从「定义了、给了 UI 文案、全项目没有
  一处发出」变成真的有生产者；新增 `tests/unit/loss-coverage.test.ts` 把「计划期算不
  出来的损失码」断言成一份记录在案、分门别类的清单，两个方向都必须刻意修改。
- 连带修掉两处同族的静默：`frame-selected` 此前用「媒体类别变了」判定，于是**每一个
  视频 → GIF** 都显示「将从动态内容中选取一帧」；图片目标的音轨容量把「非多轨 + 源有
  音频」读成了能装一条，于是带声音的视频转 GIF/JPEG 无声丢声。
- 端到端断言补上了时序：此前的 e2e 助手连时长都没有请求过，所以没有任何一条测试看得见
  这个 bug。现在「视频 → GIF」断言逐帧 0.1 秒、总长 1 秒。
- `GIF → 视频` 方向此前把毫秒当厘秒除以 100，**整整慢 10 倍**（1 秒的 GIF 变成 10 秒的
  视频）；`GIF → GIF` 重编码此前逐帧取整，33ms 的帧写成 30ms，十秒的动图无声少一秒。

**何时重新审视**：若主流渲染器普遍开始认 10 毫秒（那时下限可降到 10、上限升到 100fps），
本条的 2 与 3 就要一起改；若 `modern-gif` 换了 `delay` 的单位，`tests/unit/gif-encoder-delay.test.ts`
会先红——那条测试存在的意义就是把「单位」这个假设钉成可执行的断言。
