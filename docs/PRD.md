# PRD — Web Format Factory

## 产品目标

让用户在不把文件交给任何人的前提下，把多媒体文件从一种格式转换成另一种格式，
并且**清楚地知道这次转换付出了什么代价**。

两条主张，缺一不可：

1. **本地**——文件永不上传。
2. **诚实**——不掩饰损失，不伪造能力，不执行那些必须凭空发明内容的转换。

## 用户与使用场景

**目标用户**：处理隐私或敏感素材的人（未发布的影像、含 GPS 的照片、内部录音）、
在内网或离线环境中工作的人、以及被上传体积与等待时间困扰的普通用户。

**典型场景**：

- 从 iPhone 导出的 HEIC 照片需要交给只能读 JPEG 的系统。
- 一段 MP4 需要变成 GIF 发到不支持视频的地方。
- 要提取一段视频里的音轨，但不想把它上传到某个网站。
- 手上一组 Live Photo 需要拆成静态图和视频，或者反过来把一段视频做成 Live Photo。
- 一堆混着 FLAC / M4A / OGG 的音频需要统一成一种格式。

## 核心问题

**问题一：转换工具要求你交出文件。** 现有在线转换器几乎全部依赖服务端转码。
对于未发布的素材或含元数据的文件，这是一次不可逆的信息让渡。

**问题二：转换工具对你的损失保持沉默。** 用户通常不知道：JPEG 会丢掉 alpha；
MP4 装不下多音轨；`canvas` 路径会静默抹掉全部 EXIF 与 GPS；
把 MP3 转成 FLAC 会让文件变大而音质不变。沉默的代价由用户在事后承担。

**问题三：转换工具会「帮你」发明内容。** 把音频转成视频时生成一段频谱动画，
或者把静图拉成视频——这些是**创作**行为，却常被包装成「转换」。用户以为自己在换格式，
实际得到的是别人替他做的创作决定。

## 功能及其意义

| 功能 | 解决什么 | 为什么需要 |
| --- | --- | --- |
| 浏览器内转换（影像线） | 文件不必离开设备 | 隐私与离线场景的硬要求 |
| 浏览器内转换（音频线） | 同上 | 同上 |
| 按内容识别格式（魔数嗅探） | 扩展名错标是常态 | 错误识别会导致错误的转换计划 |
| 转换前的损失清单 | 用户在知情前提下决策 | 事后才知道损失，等于没有选择权 |
| **「改了什么」结果报告** | 转换后可核对 | 把黑箱操作变成一份可核对的账单 |
| 不可能转换的显式拒绝与理由 | 避免用户点了才报错 | 「找不到路径」不是人能据以行动的理由 |
| 有损源的增益警告 | 阻止无意义的「升级」 | FLAC 不能恢复 MP3 已经丢掉的数据 |
| Live Photo 双向封装 | 它不是一个文件而是一个文件包 | 常规转换器完全忽略这类文件 |
| 批量转换与打包下载 | 实际使用总是成批的 | 单文件场景已经被系统自带工具覆盖 |
| 离线可用（PWA） | 内网、飞行、无网络环境 | 与「本地」主张同源 |

## 功能之间的关系

```
        魔数嗅探 ──> 媒体类别判定 ──┬──> 直接转换（同类别）
                                    └──> 投影（跨类别）──> 损失标注 ──> 转换计划
                                                                        │
   不可能转换清单 ──（禁用 + 理由 + 替代格式）                            │
                                                                        v
                                                            执行 ──> 结果报告（前后差异）
```

- **嗅探**决定媒体类别，**类别**决定可达的目标集合。
- **损失标注**是执行计划的一部分，不是事后提示——它随计划一起呈现给用户。
- **结果报告**用同一套探测设施对产物再探测一次，形成闭环。
- **不可能转换清单**与前两者是同一份数据的三种视图（禁令、理由、替代）。

## 范围与非目标

### 范围内

- 18 种目标格式的互转（见 `README.md`）
- 与转换直接相关的编码参数：编码器、质量、关键帧间隔、硬件加速偏好、
  是否保留透明通道、无损开关、GIF 调色板与抖动、采样率、声道
- 元数据搬运（EXIF / XMP / ICC / ID3 / Vorbis comment / QuickTime keys）
- Live Photo 的识别、拆包与重新封装（Apple 与 Google 两种形态）

### 范围外（明确排除）

- **分辨率缩放、帧率调整、裁剪、旋转、截取片段、滤镜、拼接、调色**——
  这些是编辑，不是转换。引擎做得到，产品层不暴露。
- **从静图生成动图或视频**、**从音频生成视频**——需要凭空发明内容。
- 服务端处理、账户、云存储、分享链接。

### 不可能转换清单（必须禁用并给出理由）

| 转换方向 | 理由 | 替代 |
| --- | --- | --- |
| 音频 → 视频 / 动图 | 需要发明视觉内容 | 提供音频格式 |
| 静图 → Live Photo | Live Photo 的定义含视频成分 | 提示补拖入配对视频 |
| 静图 → 动图 | 帧序列不存在 | 提供静图格式 |
| 音频 → 静图 | 类别不匹配 | 提供音频格式 |
| 静图 → 视频 | 需要运动成分 | 提供静图格式 |

**边界情形的裁定**：`Live Photo → 静图` 与 `Live Photo → 视频` 是**允许**的，
但标记为 `projection`（投影）——因为它们丢弃了另一半。若用户另拖入一个配对视频，
则 `静图 + 视频 → Live Photo` 变为可行，UI 应当主动提示这条出路。

**动图不是静图**：`动图 → Live Photo / Motion Photo` **是允许的**，标记为 `projection`。

这条曾经被写在代码里判为不可行，理由是 `needs-motion-component`——而那条理由的文案说的是
「静态图没有运动……单张图片无法提供视频的那一半」。GIF 恰恰不是单张图片。一段帧序列本来
就同时具备成对形态要的两半：首帧作静图（与「裸视频只能交出第一帧」是同一种妥协），
帧序列重编码成真正的短片。**两半都取自它自己的像素，没有一处是凭空发明**——按上面那把尺子，
它本来就不该在那张表里。
