# Research — GIF 的帧时序：单位、栅格，以及那条 20 毫秒的下限

- **日期**：2026-09-26
- **环境**：macOS、`modern-gif@2.1.0`、`mediabunny@1.60.0`、ffmpeg/ffprobe 9.0.1、Chromium（Playwright）
- **起因**：用户报告「视频转 GIF 时，产物 GIF 的帧率会很低，没有匹配视频的帧率」。
- **状态**：结论有实测支撑（§2），并已在端到端测试里钉住。**其中 20 毫秒那条下限是外部证据，不是本地实测**——本文把两者分开写，因为它们的确信程度不同（§3）。

**一句话结论**：不是帧率丢了，是**时间单位错了 10 倍**。`modern-gif` 的 `delay` 收的是**毫秒**，而引擎传的是厘秒；每一帧的延迟因此都写成 `0`，渲染器再把 `0` 抬成 100 毫秒——产物实际播放约 10fps。修法是把内部单位统一成毫秒、把每次延迟吸附到 10 毫秒栅格上（因为编码器写盘时**向零截断**），并承认第二个事实：**20 毫秒是渲染器认的下限，不是格式的下限**，所以 50fps 是 GIF 能如实播放的上限。

---

## 1. 方法

三条互相独立的证据，缺一条都不足以定性：

1. **直接驱动编码器，回读字节**（§2）。`scripts/probes/gif-delay-unit.mjs`：给 `Encoder` 若干个 `delay`，再逐条读出产物里 Graphic Control Extension 的 `delayTime` 字段。这是唯一能同时回答「单位是什么」和「写盘时做了什么」的办法。
2. **驱动物理解码器**。同一个库的 `decodeFrames()` 把 `delayTime` 读回毫秒，用来确认两侧对称。
3. **对真实产物用 ffprobe**。GIF 的时序就写在容器里，`ffprobe -show_entries frame=duration_time` 会逐帧读出来。10fps 的样本应当读出 10 × `0.100000`。

## 2. 单位是毫秒，写盘时向零截断

`modern-gif@2.1.0` 的两处实现：

- 解码 `dist/index.mjs:212`：`frame.delay = (graphicControl.delayTime || 10) * 10` —— 厘秒 → 毫秒。
- 编码 `dist/index.mjs:1010`：`writer.writeUnsigned(delay / 10)` —— 毫秒 → 厘秒，而 `writeUnsigned` 里是位运算（`value & 255` / `value >> 8 & 255`），**对小数而言就是向零截断**。

实测（`node scripts/probes/gif-delay-unit.mjs`）：

| 传入 `delay` | 写进文件的 `delayTime` | 解码器读回 | 这一行代表 |
|---|---|---|---|
| `3` | **0** | 100ms | 引擎旧代码对 30fps 源算出来的值 |
| `2` | **0** | 100ms | 引擎旧代码对 60fps 源算出来的值 |
| `17` | 1 | 10ms | 60fps 换算成毫秒后——**截断，不是四舍五入** |
| `20` | 2 | 20ms | GIF 的可用下限 |
| `25` | 2 | 20ms | 不是 10 的整数倍 |
| `30` | 3 | 30ms | GIF → GIF 路径当时传的值（碰巧是对的） |
| `33` | 3 | 30ms | 33.3ms 的帧 |
| `100` | 10 | 100ms | 10fps |

两个结论：

- **单位是毫秒**。传厘秒，等于把每个延迟都缩小 10 倍；`Math.round(0.033 * 100) = 3`，而 `3/10 = 0.3`，截断成 `0`。
- **截断是向零的，不是四舍五入**。所以凡是交给编码器的延迟都必须先落在 10 毫秒的整数倍上——否则每帧都少一点，累积起来是**系统性漂移**（33.3 → 30 就是 10%）。把规则做在栅格上，截断就从一个会咬人的行为变成一次空操作。

## 3. 20 毫秒那条下限：来源是渲染器，不是格式

**这一条不是本地实测**，是引用。GIF 规格允许 `delayTime` 为 0 或 1（即 10 毫秒），浏览器却不照着放：

- IE 遇到帧时长 ≤ 50ms 的 GIF 会拖到 100ms；IE10 起把能支持的帧率提高到**最小 20ms**，低于它的值仍然被抬到 100ms。
  出处：[IEInternals — Trivia: Animated GIF Timing](https://learn.microsoft.com/en-us/archive/blogs/ieinternals/trivia-animated-gif-timing)
- 解码器这一侧的对应行为可以直接看到：`decodeFrames` 里 `delayTime || 10` —— `delayTime` 为 0 时读回 **100 毫秒**（§2 表格第一行），而不是 10。

保守地按这条规则办：**下限取 20 毫秒，于是 50fps 是 GIF 能如实播放的上限**。不按它办的话，「10 毫秒的帧」不会变成更流畅的动画，只会变成一帧播 100 毫秒的动画——比慢更糟，因为它是不均匀的。

> 没有本地实测的原因：渲染节奏是复合过程（解码、合成、刷新率），用截图或 `requestAnimationFrame` 采样得到的是整条链路的抖动，不是纯粹的 GIF 帧间隔。它的信噪比不足以支撑一个比外部证据更强的结论，所以这里不退而求其次。

## 4. 为什么这个 bug 能在浏览器里活到今天

样本 `tests/fixtures/generated/av.*` 恰好是 **10fps**：

- 正确值 = 100 毫秒 = `delayTime` 10；
- 错误值 = 1 厘秒 = `delayTime` 1；
- 而 `delayTime` 1 **低于 20 毫秒下限**，被渲染器抬到 100 毫秒——**看起来完全正确**。

产物文件说的却是「10 帧、总长 0.1 秒」，而浏览器把它演成了 1 秒。也就是说：这个错误在界面上不可见，只在**产物的字节**里可见。当时的 e2e 只断言产物「是一个 GIF」（`probe.codecs` 含 `gif`），连时长都没有请求过，于是没有任何一条测试能看见它。

这是本轮最值得记下来的一条：**「看起来对」和「文件里写着什么」是两件事，而只有后者能被断言。**

## 5. 对项目的意义

1. **单位在引擎内统一成毫秒**，并把「毫秒」写进 `DecodedFrame.delay` 的文档——旧文档写的是「centiseconds, as stored in the GIF」，而两个生产者给的单位其实一个毫秒、一个厘秒。文档撒谎比没有文档更糟。
2. **延迟一律吸附到 10 毫秒栅格**，且按**累积时间戳**对齐而不是逐帧各自取整。逐帧取整会让 29.97fps 的源快 11%、总时长短 11%；累积对齐既不漂，又让编码器的截断成为空操作。
3. **20 毫秒下限写进格式注册表**（`GIF_FRAME_TIMING`），引擎和损失模型都读它那一份——ADR-011 的教训是刻度只能保留一份。
4. **源快于 50fps 时只能牺牲一边**：保帧数就会放慢（60fps 的 1 秒变成 1.2 秒），保时长就要丢帧。项目选的是**保时长、丢帧**，并且如实报告——因为「合规到格式装得下的范围」是**损失**，不是**编辑**：用户没有选择任何帧率。
5. **帧时序的损失必须算出来再说**，不能写死：25fps 恰好落在栅格上，它就不该看到任何时序警告。

## 6. 复现方法

```bash
# 1. 单位与截断（本地实测，§2 那张表）
node scripts/probes/gif-delay-unit.mjs

# 2. 单位这条契约的回归测试
pnpm vitest run tests/unit/gif-encoder-delay.test.ts

# 3. 时序规则（栅格、累积对齐、抽帧合规）
pnpm vitest run tests/unit/gif-timing.test.ts

# 4. 真实产物的时序：需要样本与浏览器
pnpm fixtures
pnpm test:e2e tests/e2e/convert.spec.ts -g "GIF"

# 5. 手工核对一份产物（10fps 的样本应读出 10 × 0.1）
ffprobe -v error -show_entries frame=duration_time -of csv=p=0 out.gif
```

> ffprobe 的两个坑，都会以「空列表」的形式出现，而空列表看起来像「零帧」而不是「读错了」：
> 逐帧字段要用 `duration_time`（`pkt_duration_time` 对 GIF 与 WebM 都是空的）；`format` 段与 `frame` 段不能在同一条命令里用 `-of json` 请求，那样 `frames` 会是一串空对象。
